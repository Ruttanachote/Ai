# ซ่อมฐานรากก่อนขยาย SalesFlow สู่ Delivery และ MA

Stream SalesFlow มีโครงที่ถูกทางแล้ว คือ lifecycle ครบตั้งแต่ Opportunity ถึง MA, กฎเปลี่ยนสถานะบังคับที่ server, การอนุมัติราคาที่ผูกกับเวอร์ชันไฟล์ และใช้ M365 เป็นแกน แต่ช่องว่างสำคัญไม่ได้อยู่ที่ "ฟีเจอร์ที่ยังไม่มี" อยู่ที่สามเรื่องซึ่งต้องแก้ก่อนสร้างโมดูล Delivery/MA ทับลงไป เรื่องแรกคือ **ข้อสมมติด้าน M365 หลายจุดในเอกสารออกแบบใช้ไม่ได้ตามเอกสารทางการ** ได้แก่ การอ่าน Named range ของ Excel แบบ app-only ซึ่ง Graph ระบุว่า "Not supported", การโพสต์ Teams channel แบบ app-only ซึ่งทำได้เฉพาะงาน migration และการแปลงแท็บ Quotation เป็น PDF ที่ติดเพดานไฟล์ 2 MB และเลือกชีตไม่ได้ เรื่องที่สองคือ **ความถูกต้องของข้อมูลการขาย** ระบบยังไม่ได้ผูก "ราคาที่อนุมัติ" เข้ากับ "ราคาที่ยื่นจริงหรือ PO ที่ได้" probability ยังเก็บเป็นข้อความช่วง จึงคำนวณ weighted pipeline ไม่ได้ และลูกค้ายังเป็น free text จึงทำ Account 360 หรือ MA renewal ตามลูกค้าไม่ได้ เรื่องที่สามคือ **ยังไม่มีข้อมูลตามระเบียบพัสดุภาครัฐที่กระทบเงินโดยตรง** ได้แก่ วิธีจัดซื้อ, เลขโครงการ e-GP, ช่วงอุทธรณ์ 7 วันทำการ, หลักประกัน 5%, ค่าปรับรายวันกับเพดาน 10%, วันตรวจรับ, ภาษีหัก ณ ที่จ่าย 1% และปีงบประมาณ ทั้งที่ตั้งแต่ **1 ต.ค. 2569** ทุกวิธีจัดซื้อรวมถึงเฉพาะเจาะจงต้องทำบน e-GP ครบทุกขั้น รายงานนี้จึงเสนอให้ขยาย MVP เดิมเป็น "MVP+" ที่รวม P0 สิบรายการ ได้แก่ เส้นทางอ่าน Excel แบบ delegated, approval ที่ตรวจจับความเปลี่ยนแปลงหลังอนุมัติได้, Account master, probability ที่เป็นตัวเลขพร้อม forecast category, tender sub-workflow, ปฏิทินวันทำการไทย และทะเบียนหลักประกัน/ค่าปรับ จากนั้นค่อยต่อด้วย PSA (booking, EVM, milestone billing) และ ITSM (SLA สองนาฬิกา, renewal ตาม notice deadline และปีงบประมาณ) ใน P1 ส่วน P2 คือ analytics และ automation ขั้นสูง

## สามข้อสมมติด้าน Microsoft 365 ที่ต้องแก้ก่อนเขียนโค้ด

ข้อที่อันตรายที่สุดคือแผน §3.2 ที่ให้ background job อ่าน `Total_Revenue`, `Total_COGS`, `GP_Percent` ผ่าน Graph Workbook API หน้า permission ของ `workbook: createSession` และ `nameditem: range` ระบุว่า Application permission เป็น **"Not supported"** รองรับแค่ delegated `Files.ReadWrite` ([createSession](https://learn.microsoft.com/graph/api/workbook-createsession); [nameditem range](https://learn.microsoft.com/graph/api/nameditem-range)) แปลว่าการใช้ token แบบ `Sites.Selected` app-only ตามที่เขียนไว้ไม่ใช่เส้นทางที่ Microsoft รับรอง นอกจากนี้ session ของ workbook หมดอายุหลังว่างราว 5 นาที (persistent) หรือ 7 นาที (non-persistent) และ Microsoft แนะนำให้ส่ง request ไปที่ workbook เดียวกัน **ตามลำดับ ไม่ขนาน** เพราะถ้าส่งขนานกันจะเกิด throttling และ merge conflict ([Excel resource](https://learn.microsoft.com/graph/api/resources/excel); [Workbook best practices](https://learn.microsoft.com/graph/workbook-best-practice)) ทางแก้ที่เหมาะคือให้อ่านด้วย **token ของ SM เอง** ตอนกด "Sync ตัวเลข" หรือ "ส่งขออนุมัติ" แล้วใช้การดาวน์โหลดไฟล์ไปแยกวิเคราะห์ที่ server (openpyxl/ExcelJS อ่านค่า cached ของ defined names) เป็นทางสำรอง ระบบควรอ่าน workbook อย่างเดียวและไม่เขียนเซลล์ผ่าน API เด็ดขาด เพราะการเขียนขณะมีคนแก้ไฟล์อยู่จะเจอ `accessConflict` ([Excel error handling](https://learn.microsoft.com/graph/workbook-error-handling))

ข้อที่สองคือ §3.3 ข้อ 6 ที่ให้แปลงแท็บ Quotation เป็น PDF endpoint `?format=pdf` มีเพดาน **2 MB ต่อไฟล์ต้นทาง** และไม่มีพารามิเตอร์เลือกชีต ([Download in another format](https://learn.microsoft.com/graph/api/driveitem-get-content-format)) ไฟล์ Cost Sheet ที่ใส่โลโก้และหลายแท็บจะเกินเพดานนี้ได้ง่าย และ Cost Sheet ภายในอาจหลุดไปถึง Sale ทางที่ถูกกว่าคือให้แอปสร้าง PDF ใบเสนอราคาเองจาก **snapshot ที่อนุมัติแล้ว** ด้วย HTML template และฟอนต์ไทย ผลคือเอกสารที่ส่งออกตรงกับตัวเลขที่ผู้บริหารอนุมัติทุกตัว และไม่ต้องพึ่ง Excel conversion

ข้อที่สามคือ Teams กับ Outlook ในตาราง §6 `ChannelMessage.Send` เป็น delegated เท่านั้น ส่วน application permission ใช้ได้ "only for migration" ([channel: post messages](https://learn.microsoft.com/graph/api/channel-post-messages)) background job รายชั่วโมงจึงโพสต์แจ้งเตือนเข้าช่องทีมด้วย Graph ไม่ได้ ทางเลือกคือ Teams bot หรือ Workflows (Power Automate) เพราะ Incoming Webhook/Office 365 Connectors ถูกปลดในปี 2026 แม้แหล่งข้อมูลจะบอกวันสุดท้ายไม่ตรงกัน ([MS Q&A](https://learn.microsoft.com/en-us/answers/questions/5854971/will-teams-incoming-webhooks-stop-delivering-alert)) ส่วน `POST /onlineMeetings` สร้าง **ประชุมลอยที่ไม่อยู่ในปฏิทินใคร** และถ้าใช้ app-only ต้องให้ admin สร้าง Application Access Policy ให้ด้วย ([Create onlineMeeting](https://learn.microsoft.com/graph/api/application-post-onlinemeetings)) ประชุม Handover จึงควรสร้างเป็น calendar event ที่ตั้ง `isOnlineMeeting=true` ในนามของ PMO ที่กดปุ่ม Outlook Actionable Messages ยังใช้ได้ในปี 2026 แต่ **ตั้งแต่ 8 มิ.ย. 2026 รองรับเฉพาะ Entra ID token** การ์ดต้องใช้ `Action.Execute` กดปุ่มในอีเมลที่เก่ากว่าหนึ่งเดือนไม่ได้ ใช้ใน OWA บนมือถือไม่ได้ และใช้ไม่ได้เมื่ออีเมลผ่าน gateway แบบ Mimecast ([Actionable Messages overview](https://learn.microsoft.com/outlook/actionable-messages/); [AM FAQ](https://learn.microsoft.com/outlook/actionable-messages/actionable-messages-faq); [Enable Entra token](https://learn.microsoft.com/outlook/actionable-messages/enable-entra-token-for-actionable-messages)) ดังนั้นช่องทางหลักของการอนุมัติต้องเป็นหน้าในแอป อีเมลแต่ละฉบับมี deep link ที่ใช้ SSO และค่อยเพิ่ม AM ระดับ Organization เป็นเฟสสอง

เรื่องสิทธิ์ก็ต้องปรับเช่นกัน ถ้าให้ Entra consent `Mail.Send` แบบ application ทั้ง tenant แอปจะส่งอีเมลในนามใครก็ได้ ควรจำกัดสิทธิ์ด้วย **Exchange Online RBAC for Applications** ซึ่งเข้ามาแทน Application Access Policies แล้ว โดยกำหนด management scope ให้มีแค่ mailbox `salesflow@` ([Learn: application access policies](https://learn.microsoft.com/en-us/exchange/permissions-exo/application-access-policies); [Office365ITPros](https://office365itpros.com/2026/02/17/mail-send-rbac-for-applications/amp/)) และต้องคุมจำนวน request พร้อมกันไม่เกิน 4 ต่อ mailbox ([Throttling limits](https://learn.microsoft.com/graph/throttling-limits)) การให้สิทธิ์ `Sites.Selected` ระดับไซต์ต้องให้ admin ที่ถือ `Sites.FullControl.All` เป็นคนทำ และการตั้งสิทธิ์ระดับ folder จะ **ทำลาย permission inheritance** ([Selected permissions overview](https://learn.microsoft.com/graph/permissions-selected-overview)) แนวคิด "ล็อกโฟลเดอร์ที่ยังไม่ถึงสถานะ" ใน §3.1 จึงควรเปลี่ยนเป็น **สร้างโฟลเดอร์เมื่อโครงการถึงสถานะนั้น** แล้วบังคับกฎในแอปแทน การตรวจจับว่าไฟล์ถูกบันทึกก็มีข้อจำกัด subscription บน SharePoint/OneDrive for Business ทำได้เฉพาะ drive root, lifetime ไม่ถึง 30 วัน และต้องเรียก `delta` ต่อเพื่อดูว่าไฟล์ไหนเปลี่ยน ([Create subscription](https://learn.microsoft.com/graph/api/subscription-post-subscriptions); [driveItem delta](https://learn.microsoft.com/graph/api/driveitem-delta)) ส่วน App Roles ยังเป็นทางเลือกที่ถูก แต่ถ้าจะ assign role ให้ group ต้องมี Entra ID P1/P2 และระบบไม่ส่งต่อสิทธิ์ให้ nested group ([Assign users and groups](https://learn.microsoft.com/entra/identity/enterprise-apps/assign-user-or-group-access-portal)) ถ้า disable role โดยไม่ลบ assignment role นั้นจะยังมากับ token ([Add app roles](https://learn.microsoft.com/entra/identity-platform/howto-add-app-roles-in-apps)) ข้อสุดท้ายคือ PDPA ปัจจุบัน Thailand ยังอยู่ในกลุ่ม "Future Local Region" ของ M365 ([M365 data residency](https://learn.microsoft.com/en-us/microsoft-365/enterprise/m365-dr-overview)) ข้อมูลผู้ติดต่อลูกค้าจึงน่าจะเก็บอยู่นอกประเทศ บริษัทควรบันทึกเรื่องนี้ใน RoPA และระบุฐานการโอนข้อมูลข้ามแดนให้ชัด

## Pipeline ยังเป็นป้ายสถานะ ยังไม่ใช่เครื่องมือพยากรณ์

ใน `model.ts` ค่า `prob` เป็นข้อความ `'40–50%'` จึงคำนวณ **weighted pipeline ไม่ได้** และ stage กับความมั่นใจถูกรวมไว้ในฟิลด์เดียว CRM ที่โตแล้วแยกสามอย่างนี้ออกจากกัน คือ stage (ตำแหน่งในกระบวนการ), probability (ตัวเลขตาม stage) และ forecast category (Pipeline / Best Case / Commit / Closed / Omitted) ซึ่งผู้ขายเปลี่ยนเองได้โดยไม่ต้องเปลี่ยน stage ([Salesforce Ben](https://www.salesforceben.com/forecast-categories-in-salesforce-everything-you-need-to-know/)) HubSpot คำนวณ weighted amount เป็น Amount × Deal probability และใช้เป็นมุมมองพยากรณ์เริ่มต้น ([HubSpot KB](https://knowledge.hubspot.com/forecast/set-up-the-forecast-tool)) ทุกระบบบังคับ "exit criteria" ต่อ stage เช่น Salesforce Path กำหนด key fields ได้สูงสุด 5 ช่องต่อ stage แล้วใช้ validation rule บังคับกรอกตอนเลื่อน stage ([Salesforce Help: Path](https://help.salesforce.com/apex/HTViewHelpDoc?id=path_overview.htm)) บทเรียนจาก HubSpot ที่ควรเลี่ยงคือ required property จะถูกตรวจเฉพาะตอน "ย้าย" stage ถ้า "สร้าง" ดีลลง stage ปลายทางตรงๆ จะข้ามการตรวจไปได้ ([HubSpot Community](https://community.hubspot.com/t5/HubSpot-Ideas/Mandatory-properties-on-Deal-STAGES-get-skipped-when-creating-a/idc-p/578789/highlight/true)) `allowedMoves()` ของ SalesFlow ตรวจแค่สิทธิ์ตาม role ยังไม่ตรวจความครบของข้อมูล จึงต้องเพิ่ม `validateExit(project, toStage)` ที่ server และเรียกใช้ทั้งตอน create, edit และ move

Close Lose เป็นอีกจุดที่ข้อมูลรั่ว ระบบปัจจุบันบังคับใส่เหตุผลเฉพาะตอน **เปิดดีลแพ้กลับมา** ไม่ได้บังคับตอนปิดเป็นแพ้ แนวปฏิบัติคือใช้ picklist เหตุผลแพ้ **8–12 รหัส** และบังคับระบุ "คู่แข่งหลัก" เมื่อเลือกรหัสที่เกี่ยวกับคู่แข่ง ([Octave](https://www.octavehq.com/post/gtm-engineers-guide-to-closed-lost-analysis)) แหล่งเดียวกันแนะนำว่าไม่ควร reopen ดีลที่แพ้แล้ว ให้สร้างดีลใหม่ที่ลิงก์กลับไปแทน เพื่อไม่ให้ win rate ในอดีตเพี้ยน ข้อนี้ตรงกับงานภาครัฐที่ TOR ถูกประกาศใหม่อยู่บ่อย กฎ "หัวหน้ากลุ่มเปิด Close Lose กลับเป็น Pipeline" จึงควรเปลี่ยนเป็น "สร้างโครงการใหม่โดยตั้ง `reopenedFromId`" งานภาครัฐยังมีข้อได้เปรียบตรงที่ผลประกาศบน e-GP เปิดเผย ทีมขายจึงเก็บราคาของผู้ชนะและผู้เสนอรายอื่นได้ ถ้ามีตาราง `CompetitorBid` ระบบจะแยกได้ว่าแพ้เพราะราคาหรือแพ้เพราะโครงสร้าง เช่น แพ้ SME ที่เสนอราคาสูงกว่าเราไม่เกิน **10%** ซึ่งได้แต้มต่อตามกฎกระทรวง ฉบับที่ 2 พ.ศ. 2563 ([Post Today](https://www.posttoday.com/business/674634)) หรือแพ้สินค้า MIT ที่ได้แต้มต่อ 5% และสูงสุด 15% เมื่อผู้เสนอเป็น SME ด้วย ([Prachachat](https://www.prachachat.net/economy/news-649875))

ลูกค้าที่เป็น free text (`customer`, `endUser`) ฉุดทุกโมดูลที่ตามมา ทั้ง Account 360, การรวมสินทรัพย์หมดประกันของลูกค้าเดียวกันเป็นใบเสนอราคา MA ใบเดียว และ win rate ตาม sector ระบบควรมี `Account` ที่ใช้ **เลขประจำตัวผู้เสียภาษี 13 หลัก** เป็น dedupe key และมี `parentAccountId` สำหรับลำดับกระทรวง → กรม → หน่วยงาน ควรแยกผู้ออก PO (`customerAccountId` ซึ่งอาจเป็น prime contractor หรือ distributor) ออกจากหน่วยงานที่ใช้ระบบจริง (`endUserAccountId`) และควรมี `ProjectContactRole` ที่กำหนด primary contact ได้หนึ่งคน ตามแบบ OpportunityContactRole ของ Salesforce ([Salesforce Help: Contact roles](https://help.salesforce.com/HTViewHelpDoc?id=contactroles.htm)) รายการ role ควรมี role เฉพาะของงานรัฐอย่าง "กรรมการ TOR" และ "กรรมการตรวจรับ" เพราะหนังสือแจ้งหมดประกันและการนัดตรวจรับต้องระบุชื่อผู้รับ

ยังมีอีกสามเรื่องที่ทำให้นับยอดและพยากรณ์ผิด เรื่องแรกคือ `collaborators: string[]` แบ่งเครดิตให้หลายทีม DT ไม่ได้ Salesforce แยก **revenue split ที่ต้องรวมเป็น 100%** ซึ่งนับเข้า quota ออกจาก overlay split ที่รวมเกิน 100% ได้และไม่นับเข้ายอดบริษัท ([Trailhead: Opportunity Splits](https://trailhead.salesforce.com/content/learn/modules/leads_opportunities_lightning_experience/sell-as-a-team-and-split-the-credit)) ถ้าไม่มี split ยอดของ DT4-1 กับ DT2-3 ที่ทำโครงการเดียวกันจะนับซ้ำใน dashboard เรื่องที่สองคือ `Team.annualTarget` อย่างเดียวไม่พอ Dynamics 365 กำหนด quota ต่อเจ้าของต่องวด ให้ manager adjust ได้โดยบันทึกเหตุผล และถ่าย snapshot ได้ถี่สุดวันละครั้งเพื่อเทียบ "ที่เคยบอกไว้กับตอนนี้" ([Microsoft Learn: View a forecast](https://learn.microsoft.com/en-gb/dynamics365/sales/view-forecasts); [Adjust values in a forecast](https://learn.microsoft.com/en-gb/dynamics365/sales/adjust-values-in-forecast)) SalesFlow ไม่จำเป็นต้องมีทั้งหมดนี้ในวันแรก แต่ควรมี `PipelineSnapshot` รายสัปดาห์ตั้งแต่ MVP+ เพราะถ้าไม่มี snapshot จะคำนวณ slippage, forecast accuracy และ stage conversion ย้อนหลังไม่ได้เลย เรื่องที่สามคือ pipeline coverage ต้องตั้งเป้าตาม win rate จริง เป้าที่ใช้กันคือประมาณ 1 ÷ win rate เช่นราว 4 เท่าเมื่อ win rate 25% ([Abmatic](https://blog.abmatic.ai/what-is-pipeline-coverage-ratio)) ตัวเลขอ้างอิงเหล่านี้มาจากบล็อกของ vendor และไม่มี benchmark เฉพาะ SI ไทย บริษัทจึงควรวัดค่า baseline ของตัวเองก่อนตั้งเป้า

## การอนุมัติราคายังไม่ได้ผูกกับราคาที่ยื่นจริงหรือ PO ที่ได้

แกนของ deal desk ใน SalesFlow ดีแล้ว คือมี routing ตาม GP/มูลค่า, snapshot, ล็อกไฟล์ และบังคับเหตุผลเมื่อตีกลับ ช่องโหว่ที่สำคัญที่สุดอยู่ **หลังอนุมัติ** เมื่อ SM แก้ Excel หลังได้รับอนุมัติ SharePoint จะสร้างเวอร์ชันใหม่ แต่ระบบไม่รู้ว่าตัวเลขที่จะส่ง Sale ไม่ใช่ชุดที่อนุมัติแล้ว นอกจากนั้น Sale ซึ่งไม่ได้ใช้ระบบยังต่อรองราคากับลูกค้าเองได้ ทำให้ PO ที่ได้มาอาจต่ำกว่าราคาที่อนุมัติ การผูกการอนุมัติกับ SharePoint version ID อย่างเดียวก็เปราะเช่นกัน เพราะเวอร์ชันเก่าอาจถูกตัดทิ้งตาม version-limit policy และการ copy ไฟล์ไม่เก็บ metadata และไม่พา version history ไปด้วยถ้าไม่สั่ง ([List versions](https://learn.microsoft.com/graph/api/driveitem-list-versions); [driveItem copy](https://learn.microsoft.com/graph/api/driveitem-copy)) วิธีที่ทนทานกว่าคือตอน submit ให้บันทึก eTag กับ version ID พร้อมค่า named range ลง DB แล้ว copy ไฟล์ไปไว้ที่ `Submitted/OPP-69-xxxx_vN.xlsx` และติด retention label แบบ `retainAsRecord` ([setRetentionLabel](https://learn.microsoft.com/graph/api/driveitem-setretentionlabel)) จากนั้นเมื่อพบเวอร์ชันที่ใหม่กว่าที่อนุมัติ ระบบตั้งสถานะ approval เป็น `stale` และปิดปุ่ม "ส่งใบเสนอราคาให้ Sale" การอนุมัติควรมี `validUntil` ตามระยะยืนราคา ตอน Close Win ระบบควรเทียบมูลค่า PO หรือสัญญากับราคาที่อนุมัติ ถ้าต่างเกินค่า tolerance ต้องขออนุมัติซ้ำหลังได้งาน (post-award re-approval) สำหรับงาน e-bidding ข้อนี้สำคัญเป็นพิเศษ เพราะผู้เสนอยื่นราคาบน e-GP ได้ **ครั้งเดียว** ([UP Medsci e-bidding steps](https://www.medsci.up.ac.th/V4/medsci_doc/Contact_Procedure/E-Bidding_Step.pdf)) ราคาที่ยื่น (`bidPrice`) จึงต้องผูกกับ approval ฉบับล่าสุดก่อนยื่น

เมื่อเทียบกับ CPQ ที่โตแล้ว ยังมีช่องว่างรองอีกหลายจุด Salesforce Advanced Approvals รองรับทั้ง parallel และ sequential และมี **Smart Approvals** ที่ข้ามผู้อนุมัติซึ่งเงื่อนไขของตนไม่เปลี่ยนเมื่อส่งใหม่ ([Trailhead: Smart Approvals](https://trailhead.salesforce.com/ja/content/learn/modules/advanced-approvals-for-admins/use-smart-approvals-to-evaluate-changes)) approval process มาตรฐานล็อก record ขณะรออนุมัติ ให้ผู้ขอ recall ได้ และให้ผู้อนุมัติตั้ง delegate ช่วงลาได้ ([Salesforce Metadata API: ApprovalProcess](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_approvalprocess.htm)) ServiceNow escalate ไปยังผู้อนุมัติสำรองเมื่อพ้นกรอบเวลา ([ServiceNow docs](https://www.servicenow.com/docs/r/order-management/approving-or-rejecting-quotes.html)) แหล่งข้อมูลฝั่ง practitioner แนะนำให้ตั้ง threshold บน **มูลค่าสัญญารวม** ไม่ใช่มูลค่ารายปี แยกเพดานส่วนลดออกจาก margin floor ซึ่ง CFO เป็นเจ้าของ และระวังสัญญาณ rubber-stamp เมื่ออัตราอนุมัติผ่านเกินราว 95% ([Kognitos](https://www.kognitos.com/blog/deal-desk/)) สำหรับ SI ที่ขายภาครัฐ เงื่อนไขที่ควรอยู่ใน approval matrix นอกจาก GP% และมูลค่า คืออัตราค่าปรับต่อวันในสัญญา, ระยะประกันที่ยาวกว่ามาตรฐาน, เงื่อนไขการจ่ายเงิน และการต้องวางหลักประกัน เพราะทั้งหมดนี้เปลี่ยนความเสี่ยงของดีลได้มากกว่า GP ที่ต่างกันสองสามจุด หลักการออกแบบคือ matrix ต้องเป็นข้อมูลใน Settings ไม่ใช่โค้ด และต้องป้องกันการอนุมัติดีลของตัวเอง (submitter ≠ approver) เพราะคนคนเดียวมีได้หลาย role

## Rebidding ต้องเปลี่ยนเป็น tender workflow ที่มีวันกำหนดตามระเบียบ

stage "Rebidding" ใน SalesFlow ยุบกระบวนการที่มีหลายขั้นและมีกำหนดเวลาตามกฎหมายไว้ในกล่องเดียว และให้ probability 70–80% เท่ากับ Forecast ทั้งที่ e-bidding เป็น "รูปแบบการขาย" ไม่ใช่ "ระดับความมั่นใจ" ลำดับบน e-GP คือ ประกาศแผน → เผยแพร่ร่าง TOR เพื่อรับฟังความเห็น → ประกาศเชิญชวน → ยื่นข้อเสนอครั้งเดียว → คณะกรรมการพิจารณา → ประกาศผู้ชนะ → ช่วงอุทธรณ์ → ลงนามสัญญา ([MFA e-bidding workflow](https://image.mfa.go.th/mfa/0/GH2PYnujXi/migrate_directory/information-20200429-164426-518819.pdf)) ผู้เสนอราคาอุทธรณ์ได้ภายใน **7 วันทำการ** หลังประกาศผล เมื่อมีผู้เสนอตั้งแต่ 2 รายขึ้นไป หน่วยงานต้องรอให้พ้นช่วงนี้ก่อนลงนาม ([Thansettakij](https://www.thansettakij.com/economy/669263)) **ตั้งแต่ 1 ต.ค. 2569** การยื่นข้อเสนอและการอุทธรณ์ต้องทำผ่าน e-GP เท่านั้น โดยปิดรับอุทธรณ์ 16:30 น. ของวันสุดท้าย (แหล่งเดียวกัน) หนังสือเวียน **ว 714** (16 ก.ย. 2569) กำหนดให้วิธีคัดเลือกและวิธีเฉพาะเจาะจงทำบน e-GP ทุกขั้นด้วย ([yotathai ว714](https://yotathai.com/news/ว714-แนวทางปฏิบัติยื่นข้อเสนอวิธีคัดเลือกและเฉพาะเจาะจงผ่านe-gp)) และ **ว 753** กำหนดแบบอุทธรณ์อิเล็กทรอนิกส์ อธ 1/อธ 2 ([yotathai ว753](https://www.yotathai.com/news/ว753-ประเด็นที่2-แบบ-อธ2-หน่วยงานของรัฐ-รายงานความเห็นอุทธรณ์)) ผลคือดีลภาครัฐ **ทุกดีล** ไม่ใช่เฉพาะ e-bidding ต้องมีเลขโครงการ e-GP และหลักฐานการยื่น วิธีจัดซื้อพิจารณาจาก **วงเงินงบประมาณ ไม่ใช่ราคากลาง** ([yotathai 19-1-68](https://www.yotathai.com/passadu/19-1-68-1)) ถ้าวงเงินไม่เกิน ฿500,000 ใช้วิธีเฉพาะเจาะจงได้ ถ้าเกินต้องประกาศเชิญชวนทั่วไป ([PSU finance guide](https://www.psu.ac.th/surat/finance/p/mm3.pdf)) ฟิลด์ `budgetAmount` จึงใช้ทำนายรอบการขายและควรใช้เป็นตัวปรับ probability ด้วย

ข้อเสนอคือเปลี่ยน Rebidding จาก stage เป็น attribute `salesMotion = 'tender'` แล้วเพิ่มตาราง `TenderEvent` ที่บันทึกวันสำคัญทุกขั้น ในการ migrate ให้แปลงโครงการที่อยู่ stage `rebidding` เป็น `forecast` และตั้ง `salesMotion='tender'` บน board ยังแสดงป้าย "ยื่นประมูล" ได้เหมือนเดิม ทางเลือกที่ทำลายของเดิมน้อยกว่าคือคง stage ไว้แต่ให้มี probability และ forecast category ของตัวเอง และบังคับกรอก tender fields แต่ทางนี้ใช้ไม่ได้กับดีลเฉพาะเจาะจงที่ไม่เคยผ่าน "Rebidding" ทั้งที่ต้องทำบน e-GP เหมือนกัน กฎใหม่ของ Close Win สำหรับดีลรัฐคือต้องมี `egpResult='winner'` และ `appealWindowEnd < วันนี้` (หรือผู้เสนอมีรายเดียว) นอกเหนือจากไฟล์ PO หรือสัญญา การคำนวณ `appealWindowEnd` ต้องใช้ **ปฏิทินวันทำการไทย** ปฏิทินเดียวกันนี้ยังใช้กับ SLA ของ ticket, SLA ของผู้อนุมัติ และ capacity ของคน จึงควรสร้างเป็นโครงสร้างพื้นฐานกลางตั้งแต่ P0

หลังได้งาน มีตัวเลขสามกลุ่มที่กระทบเงินสดและกำไรโดยตรง แต่ปัจจุบันมีอยู่แค่บรรทัด "งวดงาน/ค่าปรับ" ใน checklist กลุ่มแรกคือ **หลักประกัน** ระเบียบข้อ 168 กำหนดหลักประกันการเสนอราคาและหลักประกันสัญญาไว้ที่ **5%** ของวงเงินงบประมาณหรือราคาพัสดุ และข้อ 169 ยกเว้นเมื่อคู่สัญญาเป็นหน่วยงานรัฐ ([BCNB summary](https://bcnb.ac.th/bcnb/uploads/documents/wg2/20180419_102318_121_0.pdf)) หน่วยงานคืนหลักประกันการเสนอราคาภายใน 15 วันหลังหัวหน้าหน่วยงานเห็นชอบผลการพิจารณา แต่ผู้เสนอราคาต่ำสุด 3 รายจะได้คืนหลังลงนามสัญญา ([RMUTL guideline 2026](https://e-cms.rmutl.ac.th/assets/upload/files/2026/04/20260401132208_62342.pdf)) ส่วนหลักประกันสัญญาคืน **ไม่เกิน 15 วันหลังพ้นข้อผูกพัน** ซึ่งในทางปฏิบัติคือหลังหมดประกัน ([yotathai w327](https://www.yotathai.com/passadu/w327)) bank guarantee กินวงเงินสินเชื่อของบริษัท ระบบจึงควรใช้ `Warranty.end + 15 วัน` เป็นตัวเตือนให้ทวงคืนหลักประกัน ควบคู่กับการเสนอต่อ MA

กลุ่มที่สองคือ **ค่าปรับ** ระเบียบข้อ 162 กำหนดว่างานจ้างที่ต้องการผลสำเร็จของงานทั้งหมดพร้อมกัน ซึ่งเป็นลักษณะปกติของงานพัฒนาระบบ ปรับเป็นจำนวนตายตัว **0.01%–0.10% ของราคาค่าจ้างทั้งสัญญาต่อวัน ขั้นต่ำ ฿100/วัน** กรณีอื่นปรับ 0.01%–0.20% ต่อวันของมูลค่าพัสดุที่ยังไม่ส่งมอบ ([ALRO](https://alro.go.th/uploads/org/central_admin/download/article/article_20200617153135.pdf)) เมื่อค่าปรับใกล้เกิน **10% ของวงเงินสัญญา** หน่วยงานต้องแจ้งคู่สัญญาเป็นหนังสือ ถ้าคู่สัญญาไม่ยอมรับค่าปรับโดยไม่มีเงื่อนไข หน่วยงานต้องบอกเลิกสัญญา (ข้อ 183, ว 83) ([yotathai ว83](https://yotathai.com/news/ว83-ค่าปรับเกินร้อยละ10-แจ้งคู่สัญญา-ผ่อนปรนหรือบอกเลิกสัญญา-ระเบียบข้อ183)) และการนับวันปรับต้องหักวันที่คณะกรรมการใช้ตรวจรับ ([OBEC audit deck](http://audit.obec.go.th/images/docs/Informations/20-8-64-5.pdf)) ตัวอย่างการคำนวณ (ของผู้เขียน): สัญญาพัฒนาระบบ ฿20M ที่อัตรา 0.10% มีค่าปรับ **฿20,000 ต่อวัน** เพดาน 10% คือ ฿2M ซึ่งเท่ากับล่าช้า **100 วัน** และค่าปรับคิดจากราคาเต็มสัญญาแม้งวดก่อนหน้าส่งมอบครบแล้ว Gantt จึงต้องเฝ้างวดสุดท้ายเป็นพิเศษ ระบบควรแสดง "penalty exposure" แบบ real-time และเตือนที่ 50% และ 80% ของเพดาน 10%

กลุ่มที่สามคือ **เงินที่ได้รับจริงต่องวด** ส่วนราชการต้องหักภาษี ณ ที่จ่าย **1%** เมื่อใบสั่งซื้อหรือสั่งจ้างมีมูลค่าตั้งแต่ ฿10,000 ([Revenue Department](https://rd.go.th/65193.html)) ส่วนลูกค้าเอกชนหัก 3% สำหรับค่าจ้างทำของ ([rd.go.th](https://rd.go.th/22904.html)) ค่าปรับมักหักจากเงินงวดด้วย ฟิลด์ `paid: boolean` ของ `Milestone` จึงกระทบยอดกับ statement ธนาคารไม่ได้ ต้องเพิ่ม `invoiceAmount`, `vat`, `whtRate`, `penaltyDeducted`, `netReceived` และวันที่ส่งมอบ ตรวจรับ และวางบิล การตรวจรับของคณะกรรมการ (ข้อ 175) เป็นตัวเริ่มนับทั้งการจ่ายเงินและระยะประกัน ([DDC manual](https://ddc.moph.go.th/uploads/publish/1422720231018040712.pdf)) ดังนั้น `Warranty.start` ควรคำนวณจาก **วันตรวจรับงวดสุดท้าย** ไม่ใช่วันที่ PM กดเปลี่ยนสถานะ

## Delivery ต้องมีสามคอลัมน์ booking สองระดับ และ RAG ที่คำนวณจากสูตร

§4 ของเอกสารออกแบบมีชิ้นส่วน PSA เกือบครบ แต่ data model ยังรองรับไม่ได้ `Project` มีแค่ `budget`, `revenue`, `cost` แบบ flat จึงตอบไม่ได้ว่า "ขายไว้เท่าไร, baseline ปัจจุบันหลัง CR เท่าไร, ใช้จริงไปแล้วเท่าไร, คาดว่าจบที่เท่าไร" แนวปฏิบัติของ PSA คือใช้ handover เป็น **validation gate** ไม่ใช่แค่ checklist ([Birdview PSA](https://birdviewpsa.com/blog/sales-to-delivery-handoff-checklist-consulting/)) และส่งต่อตัวเลขที่ขายไว้เป็น baseline ที่ทีม delivery แค่ยืนยัน ไม่ต้องกรอกใหม่ ([Teamwork.com](https://www.teamwork.com/blog/pipeline-to-project-handoff/)) Project Operations ของ Microsoft พา invoice schedule จาก quote line ไปเป็น contract line ได้ตรงๆ ([MS Learn: invoice schedule on quote line](https://learn.microsoft.com/vi-vn/dynamics365/project-operations/sales/invoice-schedule-quote-line)) SalesFlow ทำแบบเดียวกันได้ โดยดึงงวดงานจาก TOR หรือ Cost Sheet ตั้งแต่ช่วง Forecast แล้วแปลงเป็น `Milestone` ตอน Handover พร้อมดึงอัตราค่าปรับ หลักประกัน ระยะประกัน และ SLA tier ที่ขายไว้มาเป็นฟิลด์ที่มีโครงสร้าง ทีม delivery จะได้ไม่ต้องอ่านสัญญาซ้ำ

Workload heatmap ปัจจุบันเทียบชั่วโมงของคนที่มีชื่อกับ 40 ชม. คงที่ จึงยังไม่ใช่ resource management Project Operations แยก **soft booking** ซึ่งเพิ่มคนเข้าทีมแต่ไม่กิน capacity ออกจาก **hard booking** ซึ่งกิน capacity และเป็นเงื่อนไขก่อน assign task ได้ ([MS Learn: soft-book](https://learn.microsoft.com/en-us/dynamics365/project-operations/psa/resource-management-softbook-requirements)) และให้ PM ส่ง resource request ตาม role หรือ skill เพื่อให้ resource manager เสนอคน ([MS Learn: resource requests](https://learn.microsoft.com/en-us/dynamics365/project-operations/psa/manage-resource-requests)) SalesFlow มีข้อได้เปรียบเหนือ PSA ทั่วไปตรงที่ pipeline อยู่ในระบบเดียวกัน จึงคำนวณ demand ล่วงหน้าเป็น Σ(man-day ตาม role ใน Cost Sheet × probability) ของดีล Forecast/Commit ได้ แล้วเทียบกับ capacity ของแต่ละคนที่หักวันลาและวันหยุดราชการแล้ว PMO จะเห็นว่าทีม DT ไหนจะล้นก่อนชนะงาน Kantata โฆษณาความสามารถแบบนี้แต่ไม่ได้เปิดเผยสูตร ([Kantata](https://www.kantata.com/product/resource-forecasting-software)) สูตรนี้จึงเป็นข้อเสนอของผู้เขียน ด้าน utilization ผลสำรวจ SPI ปี 2026 (ข้อมูลปี 2025) ระบุว่า billable utilization เฉลี่ยลดลงเหลือ **66.4%** ซึ่งต่ำสุดเท่าที่ SPI เคยบันทึก ([Deltek/SPI](https://www.deltek.com/en/resources/articles/5-kpis-from-the-spi-professional-services-maturity-benchmark-report-every-pso-must-track-for-sustainable-growth)) แต่แหล่งต่างๆ ตั้งเป้าไม่ตรงกัน (75% หรือเกิน 80%) จึงควรให้ตั้งค่าได้ การวัดเรื่องนี้ต้องให้ timesheet ระบุ `billable` และ `activityType` และต้องมีขั้นอนุมัติ timesheet ก่อนนำไปคิดต้นทุนจริง

Project health แบบ Schedule/Effort/Payment ยังไม่มีสูตรรองรับ ทางเลือกที่ตรวจสอบได้คือ EVM: SPI = EV/PV, CPI = EV/AC, EAC = BAC/CPI และ TCPI = (BAC−EV)/(BAC−AC) ([Rework EVM](https://resources.rework.com/libraries/project-management/earned-value-management)) ข้อมูลที่มีอยู่แล้วใน `Task.hours` กับ `Task.spent` พอสำหรับ effort-based EV แล้ว ด้าน threshold ไม่มีมาตรฐานกลาง Birdview ตั้งค่าเริ่มต้นของ CPI/SPI ไว้ที่ 1 ถ้าต่ำกว่าเกณฑ์หนึ่งตัวเป็นเหลือง ต่ำกว่าทั้งสองตัวเป็นแดง ([Birdview help](https://help.birdviewpsa.com/hc/en-us/articles/115001822251)) แนวปฏิบัติด้าน governance เน้นว่า **ห้ามเปลี่ยน threshold กลางโครงการเพื่อหนีสถานะแดง** ([Institute of Project Management](https://instituteprojectmanagement.com/blog/rag-status-in-project-management/)) ระบบจึงควรล็อกเกณฑ์ตอน baseline และให้ PM override ได้โดยต้องใส่เหตุผล Risk log ควรขยายเป็น RAID ที่แยก risk, assumption, issue และ dependency มี probability × impact และวันทบทวน ([The Digital Project Manager](https://thedigitalprojectmanager.com/project-management/raid-log/)) ส่วน Change Request ต้องผูกกับ baseline version ที่สร้างขึ้นใหม่ และใช้ approval engine เดียวกับงานขายเมื่อต้องคิดราคาเพิ่มกับลูกค้า

## SLA ต้องมีสองนาฬิกา และ MA renewal ต้องนับจากปีงบประมาณของลูกค้า

ระบบ Ticket ปัจจุบันมี SLA เป็นข้อความคงที่ ("P1 4 ชม. · P2 8 ชม. · P3 3 วันทำการ") มี `dueAt` เดียว และผสม priority เข้ากับประเภทงาน (CR) ServiceNow มองต่างออกไป SLA definition เป็น template ที่มีเงื่อนไข start, stop, pause และ resume มี schedule ของเวลาทำการ (ถ้าไม่กำหนดจะนับ 24×7) และ ticket หนึ่งใบมีนาฬิกา **Response กับ Resolution แยกกัน** ([ServiceNow SLA docs](https://www.servicenow.com/docs/r/zUlSbxoxKPAWFDGUdAoSCw/bhljRzZsOOYk8M_F9ekPTQ)) workflow มาตรฐานเตือนที่ 50% และ 75% ก่อน breach ([ServiceNow community](https://www.servicenow.com/community/developer-forum/sla-reached-notification-for-50-75-100/m-p/3472455)) ส่วน ConnectWise ให้ SLA ผูกกับ agreement ของลูกค้า และหยุดนาฬิกาเมื่อสถานะเป็น "Waiting on Customer" ([ConnectWise SLAs](https://www.connectwise.com/platform/psa/slas)) ตามแนว ITIL priority ควรได้จาก impact × urgency และเป้าเวลาเป็นตัวเลขจากสัญญา ไม่ใช่จาก ITIL ([InvGate](https://blog.invgate.com/itil-priority-matrix)) ตัวอย่างเป้าของ vendor ที่เผยแพร่ เช่น P1 ตอบใน 15 นาทีและแก้ใน 4 ชม. ([Insight](https://insight.com/en_US/help/managed-services-service-levels-and-requests.html)) ชี้ให้เห็นข้อจำกัดที่ชัดของการออกแบบ **background job รายชั่วโมง** เพราะ job แบบนี้ตรวจ response SLA 15 นาทีไม่ทัน งาน SLA ต้องรันทุก 1–5 นาที และต้องอ่านจาก DB ไม่ใช่เรียก Graph ข้อมูลระยะประกันควรสะสม KB article และ Problem record ไว้ เพื่อส่งต่อให้โครงการ MA ที่ต่อจากโครงการเดิม (`parentId`) ได้ ([IT Process Maps](https://wiki.en.it-processmaps.com/index.php/Problem_Management))

จังหวะแจ้งเตือน 90/60/30/7 วันสอดคล้องกับแนวปฏิบัติทั่วไปที่เริ่มทบทวน 60–90 วันก่อนหมดอายุ หรือ 120 วันขึ้นไปสำหรับสัญญามูลค่าสูง ([ContractSafe](https://www.contractsafe.com/blog/blog/contract-renewal-best-practices); [Rework](https://resources.rework.com/libraries/post-sale-management/renewal-strategy-framework)) แต่วันที่ควรใช้เป็นตัวตั้งคือ **notice deadline** ไม่ใช่วันหมดอายุ ([Vaquill](https://www.vaquill.ai/blog/contract-renewal-tracking)) สำหรับลูกค้าภาครัฐ ตัวตั้งที่แท้จริงคือ **รอบงบประมาณ** ปีงบประมาณเริ่ม 1 ต.ค. และสำหรับปีงบ 2570 หน่วยงานต้องส่งคำขอตั้งงบภายใน **1 พ.ค. 2569** แล้ว ครม. อนุมัติรายละเอียดวันที่ 2 มิ.ย. 2569 ([InfoQuest](https://www.infoquest.co.th/2026/586746)) ถ้าประกันหมดในปีงบ N+1 ใบเสนอราคา MA ต้องถึงหน่วยงานก่อนที่หน่วยงานจะทำคำขอตั้งงบในปีงบ N ซึ่งเร็วกว่าการเตือนล่วงหน้า 90 วันหลายเดือน และแม้ได้งบแล้ว หน่วยงานยังต้องจัดซื้อผ่าน e-GP ใหม่อีกรอบ ทำให้มีความเสี่ยง "ช่วงไม่มีสัญญาคุ้มครอง" ระหว่างวันหมดประกันกับวันลงนาม MA ระบบจึงควรบันทึกจำนวนวันที่ไม่มีสัญญาคุ้มครองนี้ และติดป้าย ticket ช่วงนั้นว่า "นอกสัญญา" (คิดเงินหรือทำให้ฟรี) ส่วนราคา MA แนวอ้างอิงของ software license คือ **18–22% ต่อปีของค่า license** ([VendorBenchmark](https://vendorbenchmark.com/glossary/software-maintenance-support-fees)) แต่ไม่พบแหล่งอ้างอิงสำหรับ MA งานบริการหรือ custom development ของ SI ไทย จึงควรทำเป็น pricing helper ที่ตั้งค่า % แยกตามองค์ประกอบได้ ด้าน KPI ควรวัด GRR (ไม่เกิน 100%) แยกจาก NRR (รวม upsell) ค่ากลางของ SaaS Capital ปี 2025 คือ NRR 96% และ GRR 80% ([Klipfolio](https://www.klipfolio.com/metrics/difference/net-revenue-retention-rate-vs-gross-revenue-retention-rate/); [GigRadar citing SaaS Capital](https://gigradar.io/blog/net-revenue-retention)) ตัวเลขเหล่านี้เป็นของ SaaS จึงใช้ได้แค่เป็นกรอบอ้างอิงคร่าวๆ

## รายการปรับปรุงตามลำดับความสำคัญ

เกณฑ์จัดลำดับมีดังนี้ **P0** คือสิ่งที่ถ้าไม่ทำจะทำให้ข้อมูลผิด ผิดระเบียบ หรือ integration ใช้งานไม่ได้ และแก้ภายหลังได้ยาก (ต้อง migrate ข้อมูลหรือรื้อสถาปัตยกรรม) จึงควรรวมเข้า MVP+ **P1** คือแกนของโมดูล Delivery และ MA ที่เอกสารเดิมวางไว้ แต่ต้องมี data model ใหม่ **P2** คือ analytics และ automation ที่ต้องมีข้อมูลสะสมก่อนจึงจะมีประโยชน์

### P0 — ทำใน MVP+ (ก่อนเปิดใช้งานจริง)

| P0-9 | Account master | สร้าง `Account` (taxId, sector, parent) แทนข้อความ `customer`/`endUser` (เก็บ `customerAccountId`, `endUserAccountId`) และ migrate ข้อมูลเดิมด้วยการจับคู่ชื่อแล้วให้ admin ยืนยัน | มีหน้า Account 360 ที่รวมโครงการ ยอดชนะ และวันหมดประกัน |

| P0-11 | ข้อกำหนดสัญญาที่มีโครงสร้าง และทะเบียนหลักประกัน | `ContractTerms` (penaltyBasis, rate, min ฿100, warrantyMonths, slaTier, advance) และ `Guarantee` (bid, contract; BG, เงินสด, พันธบัตร; ค่าเริ่มต้น 5% ตามข้อ 168; วันคืนตามกำหนด) ข้อมูลนี้ต้องกรอกเป็นส่วนหนึ่งของ Handover gate | ผ่าน Handover ไม่ได้ถ้ายังไม่กรอกค่าปรับและหลักประกัน หน้า Finance แสดงยอด BG ที่ค้างอยู่ |

### P1 — โมดูล Delivery และ MA (หลัง MVP+)

| ID | สิ่งที่ต้องทำ | การเปลี่ยนแปลงที่ต้อง implement |
|---|---|---|
| P1-1 | Baseline สามคอลัมน์ | `Baseline(version, source: quote\|CR, revenue, cost, manDays by role, approvedAt)` แสดง Sold / Current baseline / Actual / EAC CR ที่อนุมัติแล้วสร้าง baseline เวอร์ชันใหม่ |
| P1-2 | Milestone lifecycle และ billing | `status: planned→delivered→accepted→invoiced→paid` พร้อม `deliveredAt`, `inspectionAt`, `acceptedAt`, `acceptanceDocId`, `invoiceNo`, `dueAt`, `vat`, `whtRate` (1% รัฐ / 3% เอกชน), `penaltyDeducted`, `netReceived` มีมุมมอง billing backlog (ตรวจรับแล้วแต่ยังไม่วางบิล) และเตือนให้เก็บหนังสือรับรอง 50 ทวิ `Warranty.start` = วันตรวจรับงวดสุดท้าย |
| P1-3 | Penalty exposure | คำนวณรายวัน: (วันล่าช้า − วันที่คณะกรรมการใช้ตรวจรับ) × อัตรา × ฐาน เตือนที่ 50% และ 80% ของเพดาน 10% ถึงหัวหน้ากลุ่ม และบันทึก `ExtensionRequest` (เหตุตามมาตรา 102, วันที่ขอ, วันที่ได้ขยาย, วันที่งดปรับ) |
| P1-4 | Resource management | `ResourceRequest(role, skills, hours, dates, status)` และ `Booking(user, project, week, hours, status: soft\|hard)` assign task ได้เฉพาะคนที่ hard-book แล้ว `capacityHours` ต่อคนต่อสัปดาห์หักวันลาและวันหยุด เพิ่มกราฟ capacity เทียบ demand ที่แยก hard, soft และ pipeline ถ่วงน้ำหนัก |
| P1-5 | Timesheet ที่อนุมัติแล้ว | สถานะ draft→submitted→approved/rejected ล็อกสัปดาห์ที่อนุมัติแล้ว มี `billable`, `activityType` และรายงานคนที่ยังไม่ส่งภายในเที่ยงวันจันทร์ |
| P1-6 | EVM และ RAG ตามกฎ | คำนวณ PV, EV, AC, SPI, CPI, EAC, TCPI ทุกสัปดาห์ ตั้ง threshold ใน Settings และล็อกตอน baseline PM override ได้พร้อมเหตุผล และเก็บประวัติ RAG รายสัปดาห์ |
| P1-7 | RAID และ CR เต็มรูปแบบ | `RaidItem` (type, P×I, response, reviewDate, linkedCR) โดยดึง risk จากช่วงขายมาตั้งต้นตอน Handover score ≥15 แจ้งหัวหน้า CR มี scheduleImpactDays, priceToCustomer, GP, เอกสารลงนามจากลูกค้า และผ่าน approval engine |
| P1-8 | SLA engine | `SlaPolicy(calendar, targets[priority: response, resolution], pauseStatuses, coverage 8x5\|24x7)` ผูกกับ ServiceContract `TicketSla` แยก response และ resolution, หยุดนาฬิกาเมื่อรอลูกค้าหรือ vendor, เตือนที่ 50%/75%/breach, job ทุก 1–5 นาที, priority = impact × urgency และแยก CR เป็น ticket type |
| P1-9 | ServiceContract และ renewal | `ServiceContract(type, start, end, noticeDays, noticeDeadline, coverage, slaPolicyId, value)` การเตือนอิงจาก notice deadline และ **ปีงบประมาณของลูกค้ารัฐ** (เสนอราคาก่อนรอบตั้งงบ) เพิ่มการเตือน "ทวงคืนหลักประกันสัญญา" ที่วันหมดประกัน + 15 วัน บันทึกวันที่ไม่มีสัญญาคุ้มครอง และทำ renewal pipeline board (120/90/60/30 วัน → เสนอราคาแล้ว → ได้ PO) |
| P1-10 | Approval matrix เป็นข้อมูล | `ApprovalRule(conditions[], approverType, stepGroup, mode: sequential\|parallel_all\|parallel_any, slaHours, escalateTo)` เงื่อนไขครอบคลุม GP%, มูลค่ารวม, อัตราค่าปรับ, ระยะประกัน, เงื่อนไขการจ่ายเงิน และ isTender เพิ่ม `ApproverDelegation`, recall และ `ApprovalEvent` (channel, onBehalfOf) |
| P1-11 | Quota และ snapshot | `Quota(owner, period, metric: booking\|gp)` และ `PipelineSnapshot` ทุกเช้าวันจันทร์ เก็บ snapshot สิ้นเดือนและสิ้นไตรมาสถาวร rollup ตาม `Team.parentCode` |
| P1-12 | Contacts, คู่แข่ง และ split | `Contact`, `ProjectContactRole` (มี role กรรมการ TOR/ตรวจรับ), `ProjectCompetitor`, `CompetitorBid` (มี flag SME/MIT) และ `OpportunitySplit` (revenue รวม 100% ตั้งแต่ Forecast ขึ้นไป, overlay ไม่จำกัด) |
| P1-13 | PDPA และ audit | บันทึก RoPA, ฐานการโอนข้อมูลข้ามแดน, retention ต่อประเภทโฟลเดอร์ และตาราง audit ที่เก็บ request-id ของ Graph, eTag และ oid ของผู้กระทำ (งานนี้ส่วนใหญ่ไม่ใช่งานเขียนโค้ด) |

## ส่วนขยาย data model ที่เสนอ

โค้ดด้านล่างแสดงเฉพาะส่วนที่ต่อจาก `src/data/model.ts` เดิม ฟิลด์ที่ไม่ได้ระบุให้คงไว้ตามเดิม

```ts
// ---- Sales core (P0) ----
type ForecastCategory = 'pipeline' | 'best_case' | 'commit' | 'closed' | 'omitted'
type SalesMotion = 'direct' | 'tender'
type ProcurementMethod = 'e-bidding' | 'e-market' | 'selection' /*คัดเลือก*/ | 'specific' /*เฉพาะเจาะจง*/ | 'gov-to-gov' | 'private'

interface Account { id: string; name: string; taxId?: string; type: 'customer'|'end_user'|'partner'|'vendor'|'competitor'
  sector: 'government'|'soe'|'enterprise'|'other'; parentAccountId?: string }

interface Project /* เพิ่มจากของเดิม */ {
  customerAccountId?: string; endUserAccountId?: string          // แทน customer/endUser แบบข้อความ
  probability: number; forecastCategory: ForecastCategory; stageEnteredAt: string
  salesMotion: SalesMotion; procurementMethod?: ProcurementMethod
  budgetAmount?: number; referencePrice?: number; egpProjectNo?: string; bidPrice?: number
  fiscalYear?: number; budgetStatus?: 'requested'|'in_bill'|'enacted'|'allocated'
  contractValue?: number; bookingDate?: string
  lossReasonCode?: string; lossReasonDetail?: string; winningCompetitorId?: string; winningPrice?: number
  reopenedFromId?: string
}
interface TenderEvent { projectId: string; type: 'tor_hearing'|'invitation'|'doc_download'|'bid_submitted'
  |'result_announced'|'appeal_filed'|'appeal_window_end'|'contract_signed'; at: string; ref?: string }
interface BusinessCalendar { id: string; workdays: number[]; hours: [string, string]; holidays: string[] }

// ---- Approval integrity (P0/P1) ----
interface ApprovalRequest { id: string; projectId: string; version: number
  snapshot: { revenue: number; cost: number; gp: number; contractValue: number }; snapshotHash: string
  spItemId: string; spVersionId: string; eTag: string; archivedCopyItemId: string
  status: 'pending'|'approved'|'rejected'|'recalled'|'stale'; validUntil?: string; submittedBy: string }
interface ApprovalEvent { requestId: string; stepId?: string; actorOid: string; onBehalfOf?: string
  action: 'submit'|'approve'|'reject'|'recall'|'delegate'|'escalate'; channel: 'web'|'email_link'|'am'|'teams'; at: string }

// ---- Contract / gov terms (P0) ----
interface ContractTerms { projectId: string; penaltyBasis: 'whole_contract'|'undelivered_value'
  penaltyRatePerDay: number /*0.0001–0.002*/; penaltyMinPerDay: number /*100*/; warrantyMonths: number
  slaTier?: string; advancePct?: number; whtRate: 0.01|0.03 }
interface Guarantee { projectId: string; type: 'bid'|'contract'|'advance'|'retention'; form: 'bg'|'cash'|'cheque'|'bond'
  issuer?: string; amount: number; issueDate: string; expiryDate?: string; returnDueDate?: string; returnedAt?: string }

// ---- Delivery (P1) ----
interface Baseline { projectId: string; version: number; source: 'quote'|'cr'; revenue: number; cost: number
  manDaysByRole: Record<string, number>; approvedAt: string }
interface Milestone /* แทนของเดิม */ { id: string; projectId: string; name: string; start: string; end: string; progress: number
  amount: number; status: 'planned'|'delivered'|'accepted'|'invoiced'|'paid'
  deliveredAt?: string; inspectionDays?: number; acceptedAt?: string; acceptanceDocId?: string
  invoiceNo?: string; invoicedAt?: string; dueAt?: string; vat?: number; penaltyDeducted?: number; netReceived?: number; paidAt?: string }
interface Booking { userId: string; projectId: string; weekStart: string; hours: number; status: 'soft'|'hard' }
interface RaidItem { projectId: string; type: 'risk'|'assumption'|'issue'|'dependency'|'decision'; title: string
  probability?: 1|2|3|4|5; impact?: 1|2|3|4|5; ownerId: string; reviewDate: string; status: string; linkedCrId?: string }

// ---- Service / MA (P1) ----
interface SlaPolicy { id: string; calendarId: string; coverage: '8x5'|'24x7'; pauseStatuses: string[]
  targets: { priority: 'P1'|'P2'|'P3'|'P4'; responseMins: number; resolutionMins: number }[] }
interface ServiceContract { projectId: string; type: 'warranty'|'ma'; start: string; end: string
  noticeDays: number; noticeDeadline: string; slaPolicyId: string; value: number; renewalOfId?: string }
interface TicketSla { ticketId: string; kind: 'response'|'resolution'; targetMins: number; startedAt: string
  pausedMins: number; breachAt: string; state: 'running'|'paused'|'met'|'breached'; warned50?: string; warned75?: string }
```

## Roadmap ที่ปรับใหม่

roadmap เดิมกำหนด MVP ไว้ 6–8 สัปดาห์ ข้อเสนอนี้ขยายเป็น MVP+ ราว 10–12 สัปดาห์ (ประมาณการของผู้เขียน ยังไม่ได้ประเมินกับทีม) เพราะ P0 ส่วนใหญ่คือการเปลี่ยน schema และสถาปัตยกรรม integration ถ้าเปิดใช้งานไปก่อนแล้วค่อยแก้ จะต้อง migrate ข้อมูลจริงที่ไม่สะอาด

| เฟส | ระยะเวลาโดยประมาณ | ขอบเขต | เงื่อนไขก่อนเริ่ม / ส่งมอบ |
|---|---|---|---|
| 0. Spike ยืนยันเทคนิค | 1–2 สัปดาห์ | ทดสอบ delegated read ของ named range, server-side parse, Exchange RBAC for Apps, webhook drive root กับ `Sites.Selected`, retention label บน copy และ PDF template ภาษาไทย | ได้ผลยืนยันว่าแต่ละเส้นทางใช้ได้ใน tenant จริง |
| 1. MVP+ | 8–10 สัปดาห์ | P0-1 ถึง P0-11 ร่วมกับขอบเขต MVP เดิม (SSO, ทะเบียน, โฟลเดอร์, Cost Sheet, อนุมัติ, dashboard) | migrate stage `rebidding`, ข้อมูลลูกค้าเป็น Account และเริ่มถ่าย PipelineSnapshot ตั้งแต่สัปดาห์แรกที่ใช้งาน |
| 2. Delivery | 8–10 สัปดาห์ | P1-1 ถึง P1-7 และ P1-10 | Handover gate ใช้ ContractTerms/Guarantee จากเฟส 1 |

| 4. Analytics และ automation | ต่อเนื่อง | P2 ทั้งหมด | มีข้อมูล snapshot และ timesheet สะสมอย่างน้อย 1–2 ไตรมาส |

## สิ่งที่ยังไม่ยืนยันและต้องตรวจก่อน hard-code

งานวิจัยครั้งนี้เข้าถึง gprocurement.go.th, cgd.go.th และ learn.microsoft.com โดยตรงไม่ได้ ข้อมูลระเบียบพัสดุจึงมาจากคู่มือของหน่วยงานและเว็บไซต์รองที่อ้างระเบียบ ส่วนข้อมูล Microsoft มาจาก repo ต้นฉบับบน GitHub ของเอกสาร Learn หลายประเด็นจึงต้องตรวจกับราชกิจจานุเบกษาหรือทดสอบใน tenant ก่อนเขียนเป็นกฎในระบบ ได้แก่ ระยะเวลาประกาศเชิญชวนตามวงเงินแต่ละช่วง (มีแหล่งเดียวที่ระบุ "≥3 วันทำการสำหรับ ฿0.5–100M"), ข้อ 182 ที่ให้ผู้รับจ้างแจ้งเหตุล่าช้าภายใน 15 วัน, เพดานเงินล่วงหน้าสำหรับเอกชน, กรอบเวลาตรวจรับและจ่ายเงิน, อัตราเงินประกันผลงาน, การคิด WHT 1% ก่อนหรือหลัง VAT และกับรัฐวิสาหกิจ, อากรแสตมป์ และว่าพ.ร.บ.งบประมาณปี 2570 มีผลจริงวันที่ 1 ต.ค. 2569 หรือไม่ ฝั่ง M365 ยังต้องทดสอบว่า webhook บน drive root ใช้กับ token แบบ `Sites.Selected` ได้หรือไม่ และ Workbook API แบบ app-only ยังใช้ได้จริงหรือไม่แม้เอกสารระบุว่า "Not supported" (แต่ไม่ควรออกแบบโดยพึ่งสิ่งนี้) ตัวเลข benchmark ทั้งหมด (win rate, coverage, utilization, GRR/NRR, ค่า MA 18–22%) มาจากต่างประเทศหรือจาก vendor ไม่มีตัวเลขเฉพาะ SI ไทย บริษัทจึงควรวัดค่า baseline ของตัวเองหนึ่งถึงสองไตรมาสก่อนตั้งเป้า

## Conclusion

ข้อสรุปที่ได้จากการวิเคราะห์นี้คือ ความเสี่ยงใหญ่ของ SalesFlow ไม่ได้อยู่ที่ฟีเจอร์ PM หรือ MA ที่ยังไม่ได้สร้าง แต่อยู่ที่ **รอยต่อ** ระหว่างแต่ละช่วง ได้แก่ ระหว่างราคาที่อนุมัติกับราคาที่ยื่นหรือ PO, ระหว่างสัญญากับ delivery (ค่าปรับ หลักประกัน งวดเงิน) และระหว่างวันหมดประกันกับรอบงบประมาณของลูกค้า เอกสารออกแบบเดิมมองว่ารอยต่อเหล่านี้เป็นแค่ไฟล์ในโฟลเดอร์หรือบรรทัดใน checklist จุดเปลี่ยนคือการทำให้ทั้งหมดเป็นข้อมูลที่มีวันที่และสูตรคำนวณ เมื่อมีแล้ว ฟีเจอร์ที่ดูซับซ้อนอย่าง penalty exposure, การเตือนต่อ MA ตามปีงบประมาณ หรือ demand ล่วงหน้าที่ถ่วงด้วย probability จะกลายเป็น query ธรรมดาบนข้อมูลที่เก็บอยู่แล้ว

ข้อได้เปรียบเชิงกลยุทธ์ของ SalesFlow เหนือการซื้อ CRM กับ PSA แยกกันคือ pipeline, delivery และ MA อยู่ในฐานข้อมูลเดียวกัน ระบบจึงปิดวงจรได้สองวงที่ซอฟต์แวร์สำเร็จรูปทำได้ยาก วงแรกคือวัด GP ที่อนุมัติ เทียบกับ GP ของ PO และ GP ตอนปิดโครงการ เพื่อปรับ template ของ Cost Sheet วงที่สองคือใช้หลักฐาน SLA ในช่วงประกันเป็นเหตุผลประกอบใบเสนอราคา MA ที่ส่งทันรอบตั้งงบ แต่ข้อได้เปรียบนี้เกิดขึ้นได้ก็ต่อเมื่อ P0 วางฐานข้อมูลไว้ถูกต้องตั้งแต่วันแรก โดยเฉพาะ snapshot ที่ย้อนกลับไปเก็บย้อนหลังไม่ได้
