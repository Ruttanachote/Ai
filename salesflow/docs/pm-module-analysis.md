# วิเคราะห์โมดูล PM (Project Delivery) — One Platform

ผู้จัดทำ: SA · ฉบับร่าง 9 พ.ย. 2569
อ้างอิง: สรุปไลฟ์ “สอนใช้ Jira สำหรับผู้เริ่มต้น” (Blue on Data) และสิ่งที่ต้นแบบมีอยู่ใน `salesflow/` ณ commit ล่าสุด

---

## 1. ขอบเขตและหลักการ

โมดูล PM เริ่มทำงานหลัง **Handover** และจบเมื่อ **ส่งมอบงวดสุดท้าย → ส่งต่อทีม MA**
หลักการออกแบบที่ได้จากไลฟ์ และปรับให้เข้ากับบริบท Stream:

| หลักการ (จาก Jira) | ความหมายใน One Platform |
|---|---|
| Source of Truth หนึ่งเดียว | แผน งาน ความเสี่ยง CR และสถานะงวดงานอยู่ในพื้นที่งานเดียว ทุกหน้าคำนวณจากข้อมูลชุดเดียวกัน |
| Transparency | ลูกค้า (ผ่านแบบฟอร์ม/รายงาน) ผู้บริหาร PMO และทีม Dev เห็นสถานะเดียวกัน |
| วางแผนง่าย | Timeline ผูกกับงวดงานในสัญญา Sprint ผูกกับกำลังคน (Workload) |
| ควบคุมคุณภาพ | Workflow บังคับขั้นตอน (Code Review → QA → UAT) และเกณฑ์ Definition of Done |
| เริ่มง่าย ค่อยซับซ้อน | Template 3 แบบ (ตามงวดงาน / Scrum / Kanban) เปิดใช้ได้ทันที ปรับแต่งได้ภายหลัง |

**สิ่งที่ One Platform ต้องทำได้มากกว่า Jira** (เพราะ Jira ไม่รู้เรื่องสัญญา): ผูกงานกับงวดงาน งวดเงิน ค่าปรับ CR ที่มีราคา OT ในวงเงิน Cost Sheet และการส่งต่อ MA

## 2. ผู้ใช้และบทบาทในโมดูล PM

| บทบาท | ใช้ทำอะไร | สถานะในต้นแบบ |
|---|---|---|
| **PM** | สร้างพื้นที่งาน วางแผน แตกงาน จัด Sprint อนุมัติ OT ติดตามความเสี่ยง รายงานลูกค้า | มี |
| **PMO (DT3-3)** | มอบหมาย PM จัด Handover ดู Portfolio ทุกโครงการ ตั้งมาตรฐาน Workflow/Template | มี |
| **หัวหน้าทีม Dev** | รับงานเข้าทีม จัดคน ดู Workload อนุมัติ OT เกินวงเงิน (ขั้นแรก) | มีบางส่วน |
| **Dev / QA / BA / UX** | ทำงานบนบอร์ด อัปเดตสถานะ บันทึกชั่วโมง เขียนการ์ด/Test case | **ยังไม่มีบทบาทนี้** — ตอนนี้คนในทีมถูกใส่เป็น role `pm` ในข้อมูลตัวอย่าง |
| **SM** | ดูความคืบหน้าโครงการที่ตัวเองขาย (อ่านอย่างเดียว) | มี (ผ่านทะเบียนโครงการ) |
| **ทีม MA** | รับงานค้างและ Bug ตอนส่งมอบ | มีบางส่วน (ยังไม่ส่งต่องานอัตโนมัติ) |
| **ลูกค้า** | แจ้งปัญหา UAT / ขอ CR ผ่านแบบฟอร์ม ดูรายงานงวด | มีแบบฟอร์ม (ยังไม่มีพอร์ทัลลูกค้า) |
| **ผู้บริหาร** | ดูสุขภาพโครงการ (RAG) และความเสี่ยงค่าปรับ | มี (Portfolio) |

> **ข้อเสนอ SA-1:** เพิ่มบทบาท **ทีมพัฒนา (`dev`)** ที่เห็นเฉพาะ “พื้นที่งานโครงการ” ที่ตัวเองเป็นสมาชิก และ “งานของฉัน” — ไม่เห็นราคา ต้นทุน หรือข้อมูลขาย

## 4. เทียบฟีเจอร์: Jira ↔ One Platform

สถานะ: ✅ มีแล้ว · 🟡 มีบางส่วน · ⬜ ยังไม่มี · ลำดับ: **P1** ควรมีก่อนเปิดใช้ · **P2** ช่วงถัดไป · **P3** ภายหลัง

### 4.1 โครงสร้างโปรเจกต์และสิทธิ์

| ฟีเจอร์ | สถานะ | หมายเหตุ / ช่องว่าง | ลำดับ |
|---|---|---|---|
| Project + Key (รหัสงาน SPP-1) | ✅ | สร้างตอนเลือก Template | — |
| Template Kanban / Scrum / Waterfall | ✅ | “ตามงวดงาน” แทน Waterfall และสร้าง Epic จากงวดให้ | — |
| สมาชิกพื้นที่งาน (Workspace members) | ⬜ | ตอนนี้ทีมคำนวณจากผู้ถูก assign — ควรมีรายชื่อสมาชิกและบทบาทในพื้นที่งาน | **P1** |
| สิทธิ์แบบ Company-managed | 🟡 | สิทธิ์ตามบทบาทของระบบมีแล้ว แต่ยังไม่มีสิทธิ์รายพื้นที่งาน (ใครแก้ Workflow / ลบงานได้) | **P1** |

### 4.2 บอร์ด สถานะ และ Workflow

| ฟีเจอร์ | สถานะ | หมายเหตุ / ช่องว่าง | ลำดับ |
|---|---|---|---|
| บอร์ดลากวาง | ✅ | รวมคีย์บอร์ด และเพิ่มงานรายคอลัมน์ | — |
| **คอลัมน์/สถานะปรับได้** (Code Review, Ready for QA, QA, UAT) | ⬜ | ตอนนี้ตายตัว 4 สถานะ ต้องมี “หมวดสถานะ” (ยังไม่เริ่ม/กำลังทำ/เสร็จ) เพื่อให้ตัวเลขรวมยังคำนวณถูก | **P1** |
| **กฎการย้ายสถานะ** (To Do ไปได้แค่ In Progress, ห้ามข้าม QA) | ⬜ | กันคนลัดขั้นตอน ตามที่ไลฟ์แนะนำ — บังคับทั้งหน้าเว็บและ API | **P1** |
| ฟิลด์บังคับตอนย้าย (เช่น ต้องใส่ผลทดสอบก่อน Done) | ⬜ | ผูกกับ Definition of Done | P2 |
| WIP limit | ✅ | เฉพาะ Kanban (4 งาน) — ควรตั้งได้รายคอลัมน์ | P2 |

## 5. ฟีเจอร์เฉพาะ One Platform (สิ่งที่ Jira ไม่มี)

| ฟีเจอร์ | สถานะ | สิ่งที่ต้องเชื่อม | ลำดับ |
|---|---|---|---|
| Epic ↔ งวดงาน ↔ งวดเงิน | 🟡 | สร้าง Epic จากงวดได้ แต่ปิด Epic ยังไม่เปลี่ยนสถานะงวดเป็น “ส่งมอบแล้ว” | **P1** |
| ความเสี่ยงค่าปรับจากงานจริง | 🟡 | ตอนนี้คำนวณจากงวดงาน — ควรใช้วันคาดเสร็จของงานใน Epic ที่ยังเปิด | P2 |
| **CR → งานใหม่** | 🟡 | CR อยู่ในแท็บโครงการและแบบฟอร์ม แต่ CR ที่ลูกค้าอนุมัติยังไม่สร้าง Epic/Story พร้อม Man-day | **P1** |
| ชั่วโมงงาน → Workload / OT | 🟡 | ชั่วโมงในการ์ดยังไม่ไหลไป Workload และ OT — ต้องมี **Worklog** (บันทึกเวลารายวัน) | **P1** |
| แบบฟอร์ม UAT → Bug | ✅ | | — |
| **ส่งต่อ MA ตอนปิดโครงการ** | ⬜ | Bug/งานค้างกลายเป็น Ticket ของ Helpdesk พร้อมลิงก์กลับ | P2 |
| RAID (ความเสี่ยง ปัญหา สมมติฐาน การพึ่งพา) ในพื้นที่งาน | 🟡 | ความเสี่ยงอยู่ในแท็บโครงการแยกกัน — ควรเป็นประเภทงานหรือรายการในพื้นที่งาน | P2 |
| รายงานความคืบหน้างวดถึงลูกค้า | 🟡 | มีเอกสารรายงานงวด — ควรสร้างจากข้อมูลจริงได้ (สัดส่วนเสร็จ ความเสี่ยง CR) | P2 |

## 6. ข้อเสนอโครงข้อมูลเพิ่ม (ต่อจาก `src/data/model.ts`)

```ts
// Workflow ปรับได้ต่อพื้นที่งาน — หมวดสถานะทำให้ Dashboard/Portfolio ยังคำนวณถูก
interface WorkflowStatus { id: string; name: string; category: 'todo' | 'doing' | 'done'; wipLimit?: number }
interface Transition { from: string | '*'; to: string; roles?: string[]; requireFields?: ('acceptance' | 'spent' | 'resolution')[] }
interface Workflow { statuses: WorkflowStatus[]; transitions: Transition[] }   // ไม่มี transition = ย้ายได้อิสระ

interface WorkspaceMember { userId: string; role: 'pm' | 'lead' | 'dev' | 'qa' | 'ba' | 'viewer' }

interface Task /* เพิ่ม */ {
  statusId: string                // แทน status แบบตายตัว
  assignees: string[]             // คนแรก = ผู้รับผิดชอบหลัก
  storyPoints?: number
  acceptance?: { text: string; done: boolean }[]
  attachments?: { name: string; spItemId: string; url: string }[]
  links?: { type: 'blocks' | 'relates' | 'duplicates'; key: string }[]
  watchers?: string[]
  history?: { at: string; who: string; field: string; from?: string; to?: string }[]
  resolution?: 'done' | 'wontdo' | 'duplicate'
  crId?: string                   // งานที่เกิดจาก CR
  maTicketId?: string             // งานที่ส่งต่อ MA
}
interface Worklog { taskId: string; userId: string; day: string; hours: number; overtime?: boolean }
interface AutomationRule { id: string; when: { type: 'transition'; to: string } | { type: 'due_in'; days: number }; then: { type: 'assign'; role: string } | { type: 'notify'; to: 'assignee' | 'pm' | 'watchers' } }
interface SprintReport { sprintId: string; committed: number; completed: number; daily: { day: string; remaining: number }[] }
```

## 8. ความต้องการที่ไม่ใช่ฟังก์ชัน

- **ประวัติและการตรวจสอบ:** ทุกการเปลี่ยนฟิลด์บันทึก History (ใคร เมื่อไร ค่าเดิม → ค่าใหม่) เก็บอย่างน้อย 5 ปีตามอายุสัญญา + ประกัน
- **ข้อมูลจริงอยู่ในฐานข้อมูล** ไม่ใช่ SharePoint — SharePoint เก็บเฉพาะไฟล์แนบและเอกสาร
- **การแก้พร้อมกัน:** ใช้ version ต่อการ์ด กันการเขียนทับเมื่อสองคนแก้พร้อมกัน
- **ขนาด:** พื้นที่งานละ 2,000+ การ์ดต้องโหลดรายการ/บอร์ดได้ใน 2 วินาที (แบ่งหน้า + โหลดตามมุมมอง)
- **มือถือ:** ทีมต้องย้ายสถานะ บันทึกชั่วโมง และตอบความคิดเห็นจากมือถือได้
- **การเข้าถึง:** ใช้คีย์บอร์ดได้ทุกมุมมอง (บอร์ดทำแล้ว) และไม่สื่อความหมายด้วยสีอย่างเดียว

## 10. คำถามที่ต้องยืนยันกับผู้ใช้

1. ทีม Dev / QA / BA จะใช้ One Platform โดยตรง หรือยังใช้ Jira อยู่และให้ One Platform ดึงข้อมูลมา (ถ้าใช้ Jira ต่อ ต้องทำ Integration แทนการสร้างบอร์ดเอง)
2. Workflow มาตรฐานของ DT มีขั้นอะไรบ้าง (เช่น To Do → In Progress → Code Review → Ready for QA → QA → UAT → Done) และต่างกันรายทีมย่อยหรือไม่
3. ใช้ Story point หรือชั่วโมงเป็นหลักในการประเมิน หรือแล้วแต่โครงการ
4. ต้องบันทึกชั่วโมงทำงานรายวัน (Timesheet) จริงหรือไม่ — กระทบทั้ง Workload, OT และต้นทุนจริง
5. ใช้ GitHub, GitLab หรือ Azure DevOps
6. ลูกค้าควรเห็นอะไรได้บ้าง (เฉพาะแบบฟอร์ม/รายงาน หรือดูความคืบหน้าแบบอ่านอย่างเดียว)
